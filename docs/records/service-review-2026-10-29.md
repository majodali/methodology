#### What is deployed

The service is one TypeScript Lambda function on Node.js 22 behind an AWS HTTP API, defined in one AWS SAM template. The HTTP API carries two routes: "ANY /mcp" for MCP over streamable HTTP, and "GET /health" without authentication. Two DynamoDB tables hold advisory leases, one serving the [live alias](https://github.com/majodali/project-orchestrator-service/blob/main/docs/classification.md) and one serving the [preprod alias](https://github.com/majodali/project-orchestrator-service/blob/main/docs/classification.md). Every call to /mcp must carry a bearer token equal to the server's MCP_AUTH_TOKEN value. With MCP_AUTH_TOKEN unset, the server refuses every /mcp call rather than accepting all callers. The service reads GitHub through an installed GitHub App holding contents-read permission only. The service holds no credential able to write any repository. The service reads one project, named by the MCP_PROJECT setting, whose default is majodali/project-orchestrator. The service serves the [Plan register](https://github.com/majodali/project-orchestrator/blob/main/docs/process/plan-register.md) only, with no other register and no comprehension model.

#### Which MCP tools exist

The service exposes six MCP tools: service_identity, plan_read, plan_lease_acquire, plan_update, plan_confirm and plan_lease_release. The tool service_identity returns the service's name, version, deployed commit and configured project. The tool plan_read returns the Plan register at a named git ref as structured nodes, for the whole tree or for one subtree. Every plan_read answer carries the commit SHA and fetch time of its source. No tool answers from a cached copy of the register: every call fetches the register from git afresh.

#### The write path

Under the write model, a plan-state update takes three calls: plan_lease_acquire, plan_update, then plan_confirm with the SHA of the session's pushed commit. The tool plan_update checks a transition against the plan model's lifecycle and the register at the given SHA, returning the exact line edit. The calling session, never the service, applies the returned edit, commits the edit and pushes the commit. The tool plan_update refuses an illegal transition, naming plan-model.md as the authority. The tool plan_update refuses an edit against a stale baseline SHA, naming both SHAs. The tool plan_confirm reports a divergence, naming the file and line, when the commit at the given SHA lacks the edit.

#### What the lease does

The advisory lease is one DynamoDB item per table, allowing one lease holder at a time. While one holder's lease is live, the service refuses a second plan_lease_acquire. A lease lasts 600 seconds by default, with any requested duration clamped to between 30 and 3600 seconds. Lease expiry is enforced by a DynamoDB condition at acquire time, not by DynamoDB's own background expiry sweep. The tool plan_confirm releases the lease on success, with plan_lease_release freeing a lease early. The advisory lease guards Plan register edits only: no tool records a claim on a task. The service authenticates a client, not a role: one shared bearer token cannot tell one orchestration role from another.

#### How a session enlists

Enlistment needs three things: a checked-in `.mcp.json` at the repository root, enableAllProjectMcpServers in `.claude/settings.json`, and MCP_AUTH_TOKEN in the session's environment. The `.mcp.json` names the endpoint, a 30000 millisecond timeout and an Authorization header expanded from MCP_AUTH_TOKEN, keeping the token out of git. The coordinating repository majodali/project-orchestrator is enlisted by a checked-in `.mcp.json` and settings file. Enlistment from the checked-in `.mcp.json` is evidenced in Claude Code cloud sessions and on the owner's local machine. A session confirms enlistment by listing the service's tools and calling service_identity.

#### How CI deploys

A pull request to the service repository runs build, lint, test and "sam validate --lint", with read-only permissions and no route to an AWS role. A merge to main assumes the deploy role through GitHub OIDC, deploys, and points the preprod alias at the new Lambda version. The [smoke test](https://github.com/majodali/project-orchestrator/blob/main/docs/plans/p2-n012-deploy-from-ci-on-merge.md#the-smoke-test-and-where-its-token-comes-from) checks /health, the tools/list contents and one lease acquire-and-release cycle against the preprod alias's Function URL. Only a passing smoke test promotes the version, by repointing the live alias at the version. A failing smoke test leaves the live alias on the previous version, with the workflow run red. GitHub OIDC supplies the deploy credentials, leaving no long-lived AWS secret in the service repository. The first green deploy run took 1 minute 40 seconds end to end, on 2026-09-06.

#### What the fallback is

The [fallback rule](https://github.com/majodali/project-orchestrator/blob/main/docs/process/enlistment.md#the-fallback-rule): a session whose service is unreachable does not retry, does not wait, and edits the Plan register by hand under the [v1 process](https://github.com/majodali/project-orchestrator/blob/main/docs/process/dispatch.md). The fallback exercise covered both failure modes, unreachable endpoint and unset token, on cloud and local surfaces, closing risk R12, service outage stops work, on 2026-09-07. In both failure modes the session started normally, with the service's tools absent from the session. Risk R12's remaining exposure is breakage between deploys, which no monitoring watches today. A degraded-but-present service, the case the no-retry rule would really face, has never been exercised. Risk R17, the harness's guidance pushing against the fallback rule, is open. Risk R17's mitigation, fallback wording in the orchestrator's role definitions, belongs to node P1-N014, role contracts adopt the v1.5.0 conduct rules, which stands at planned.

### Gaps between the state and the vision

#### Surfaces without a repository clone

No surface without a repository clone can reach the service today, because enlistment rides on a cloned repository's `.mcp.json`. The service offers no remote MCP connector: a static bearer token in a request header is the service's only client authentication. A surface without a repository clone has no checkout in which to apply the edit plan_update returns. Standing constraint 1, git remains authoritative, requires git to hold the state without naming who writes git. The session-only writer rule comes from the write model, decision 3 of the P2-N002 plan, which keeps every repository write credential out of the service. A service commit through a GitHub App with write permission would break the write model while keeping standing constraint 1. No record read for this review names Claude Code desktop as a surface where enlistment was exercised.

#### The web view and its drill-down

The service has no web view: the service exposes MCP tools and a health route only, with no human-facing page. The service plan's design sketch has the plan view updated as sessions publish, not by polling git. Without a recorded location for each node's verification evidence, the service has no source for a drill-down to code and test results.

#### The task-pull loop

The service has no tool handing out a next task, recording a task claim, or reporting task completion. Role-aware identity, needed to hand out the next task in a role, was deferred to the task-pull loop by decision 12 of the P2-N002 specification. The fallback task-claim protocol, claim release when a session dies, and reconciliation after an outage are open Backlog items for the task-pull loop. The advisory lease's behaviour under several live sessions is untested, deferred to the task-pull loop by decision 7 of the P2-N002 plan.

#### The pilot

The pilot on methodology-tools needs multi-project plan state, which the service lacks. The orchestrator Backlog places multi-project plan state with node P2-N006, migration and pilot.
